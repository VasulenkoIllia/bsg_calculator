## Key Modules Deep-Dive

### Auth (`server/modules/auth/`)
- **Routes (auth.routes.ts):**  
  `POST /login` (5/min limiter) → `POST /refresh` (20/min) → `POST /logout` → `GET /me` (Bearer) → `POST /me/password` + `/me/sign-out-everywhere` (Bearer, self-service limiter).
- **Tokens (auth.tokens.ts):**  
  JWT access tokens (HS256). Refresh tokens are opaque random strings, hashed with SHA-256 in DB, sent as `HttpOnly` cookies.
- **Controller:** Parses login creds, calls service, sets refresh cookie. `login()` returns a **union**: a full session OR a 2FA challenge (`{ twoFactorRequired, tempToken }`).
- **Service:** password verify + token issuance; the login 2FA branch + refresh rotation/grace.
- **Repository:** Email lookup, password hash check, refresh token upsert/rotate/revoke-all.
- **TOTP 2FA (Phase 8 Stage 2) — `two-factor.{service,repository,controller,schemas}.ts`:**  
  `POST /auth/2fa/verify` (10/min, TOTP **or** backup code → real session; `trustDevice` sets the `bsg_td` cookie) · `GET /auth/me/2fa` (status) · `POST /auth/me/2fa/{setup,confirm,disable,backup-codes/regenerate}` (3/min setup limiter; disable/regenerate re-auth = password + code) · `POST /users/:id/2fa/disable` (super_admin force-disable, audited). otplib (SHA1/6/30, window:1); the TOTP secret is AES-256-GCM-encrypted (`shared/totp-crypto.ts`, key `TOTP_ENCRYPTION_KEY`); backup codes + the trusted-device cookie token + the 5-min login temp token are all sha256-hashed (only hashes stored). New tables: `totp_backup_codes`, `trusted_devices`, `mfa_temp_tokens` (migrations 0018/0019).

### Companies & Deals (`server/modules/companies/`, `server/modules/deals/`)
- **Provider-aware TTL refresh:**  
  When a single company or deal is read (`GET /api/v1/companies/:id`, `GET /api/v1/deals/:id`; `GET /api/v1/companies/:id/deals` also refreshes that company, but list endpoints never refresh the rows they list) and its `lastSyncedAt` is older than `HUBSPOT_SYNC_TTL_SECONDS` (legacy name; default 300, used for monday too), the endpoint returns cached data AND schedules a non-blocking refetch from the **active** CRM via `scheduleTtlRefresh()`. With `CRM_PROVIDER=monday` the refetch is `refreshCompanyFromMonday` / `refreshDealFromMonday` (`server/modules/monday/monday.refresh.ts`): it skips unbound rows (`crmItemId` null), never acts on absence (an item that is not returned or not active leaves the row untouched), and upserts through the same code as the backfill, which advances `last_synced_at` on every sync. Next request sees fresh data.
- **Service layer (ttl-refresh usage, `companies.service.ts`, abridged):**  
  ```ts
  // runTtlRefresh = scheduleTtlRefresh from shared/ttl-refresh.ts
  const usingMonday = env.CRM_PROVIDER === "monday";
  return runTtlRefresh({
    lastSyncedAt: row.lastSyncedAt,
    ttlMs: env.HUBSPOT_SYNC_TTL_SECONDS * 1000,
    enabled: usingMonday
      ? monday.isConfigured() && row.crmItemId !== null // unbound: nothing to refresh from
      : hubspot.isConfigured(),                         // dormant HubSpot branch
    logLabel: usingMonday ? "[companies] monday TTL refresh" : "[companies] HubSpot TTL refresh",
    logContext: usingMonday ? { crmItemId: row.crmItemId } : { hubspotCompanyId: row.hubspotCompanyId },
    refresh: usingMonday
      ? () => refreshCompanyFromMonday({
          crmItemId: row.crmItemId as string,
          crmBoardId: row.crmBoardId ?? null,
          companyType: row.companyType ?? null
        })
      : async () => { /* HubSpot getCompany → map → upsert (dormant) */ }
  });
  ```
- **Listing:** Uses `buildPage()` helper with cursor pagination.
- **Public DTO:** Drops `hubspot_raw` JSONB blob from responses.

### CRM — monday.com (`server/modules/monday/`) — LIVE
The only CRM (production `CRM_PROVIDER=monday` since 2026-08-28; the code default in `env.ts` is still `hubspot`, so deployments set it explicitly). Operating manual: [`docs/CRM_INTEGRATION.md`](../CRM_INTEGRATION.md). Boards: Companies `5102466967`, Agents `5102466950`, Deals `5102466996`.

| File | Role |
|---|---|
| `monday.client.ts` | GraphQL client. Treats HTTP 200 + `errors[]` as a failure, handles JSON and HTML 429s, requires `items(ids:)` results to be mapped by id, and `assertApiVersion()` checks the pinned `MONDAY_API_VERSION` (`2026-07`) at boot. |
| `monday.types.ts` | Response types + the column-value fragment (all columns, type-specific fields). |
| `monday.columns.ts` | Fail-loud column resolution: remembered id first, then title + type; a missing or ambiguous required column throws, a missing optional one is left alone. |
| `monday.column-cache.ts` | Short (5 min) cache of resolved columns, shared by the webhook processor and the TTL refresh. |
| `monday.mapper.ts` | Item → row as two patches: `binding` (monday-owned columns, always applied) and `display` (name, type, stage…, applied only when monday is the active CRM). Unresolved columns are omitted, never nulled. |
| `monday.backfill.ts` | `runMondayBackfill` + `upsertOneCompany` / `upsertOneDeal` — the one upsert path shared by webhooks, TTL refresh and backfill. Never deletes: absence is flagged (`crm_missing_since`), and a pass that would flag more than 5% of bound rows aborts. Advances `last_synced_at` and `hubspot_modified_at` ("CRM updated") on every sync. Applies a deal's Company (M) link on every sync: only a primary bound company is accepted, an empty or unbound link leaves the deal where it is, and a deal already under any row bound to that card (alias included) is not moved. |
| `monday.refresh.ts` | Single-item TTL refresh (`refreshCompanyFromMonday`, `refreshDealFromMonday`). An item that is not returned or not active leaves the row untouched — only the backfill may conclude an item is gone. |
| `monday.maintenance.ts` | `startMondayMaintenance()`: scheduled backfill every `MONDAY_BACKFILL_INTERVAL_HOURS` (default 24; first run after `MONDAY_BACKFILL_FIRST_DELAY_MINUTES`, default 15; `0` disables it and logs a WARN) + an hourly `[monday:health]` queue log (ERROR when events exhausted their retries, WARN when the oldest pending event is over 10 minutes old, INFO otherwise). Visibility only — no paging. |

#### Webhooks (`server/modules/monday/webhooks/`)
- **webhooks.routes.ts** — `POST /api/v1/monday/webhooks/:secret` (public). The secret path segment is compared in constant time and masked in the request log; if `MONDAY_WEBHOOK_SECRET` is unset the route answers 404. No raw-body parser is needed (monday does not sign personal-token webhooks).
- **webhooks.controller.ts** — echoes the registration `challenge`; otherwise classifies the board (companies / agents / deals; other boards are skipped), builds a synthetic idempotency key, queues one row and answers 200 at once.
- **webhooks.schemas.ts** — `SUPPORTED_EVENTS` (8 canonical names: `create_item`, `change_column_value`, `change_name`, `item_deleted`, `item_archived`, `item_restored`, `move_item_to_group`, `item_moved_to_any_group`; we register 7 of them per board — all except `move_item_to_group` — so 7 × 3 boards = 21 webhooks) and `normaliseEventType`, which maps the names monday actually delivers (`create_pulse`, `update_name`, `update_column_value`, `delete_pulse`, `archive_pulse`, `restore_pulse`, `move_pulse_into_group`, …) onto them.
- **webhooks.repository.ts** — `monday_webhook_events` queue: insert-if-new on `event_key`, pending batch (backoff 30s × attempts), mark processed / failed.
- **webhooks.processor.ts** — self-rescheduling 5s poller (batch 50), started from `server/index.ts` after the API-version assertion. The payload is only a trigger: each item is re-read from the API and upserted via `monday.backfill.ts`. Delete never blindly deletes — a company that owns documents or calculators is kept and flagged (`crm_deleted_at`); archive only flags. `MAX_ATTEMPTS=5`, then `status='failed'`.
- `/ready` reports `checks.monday` (a `me` query) and `mondayWebhookQueue` (pending / failed / ages); the queue is reported but not part of readiness (`server/modules/health/health.routes.ts`).

#### Scripts
- `npm run monday:backfill` → `server/scripts/monday-backfill.ts` (idempotent, safe any time).
- `npm run monday:drift` → `server/scripts/monday-drift-check.ts` (read-only board/column check; run before structural board changes).
- `server/scripts/monday-remap.ts` — the one-time legacy-data migration tool; a fresh install does not need it.

### CRM notes (`server/modules/crm-notes/`)
- **crm-notes.service.ts** — `publishCrmNote` posts to the active CRM: a monday "update" on the deal card when the record is pinned to a deal, otherwise on the company card. An unbound row is refused (`CrmUnreachableError`), never written to the other CRM; its message still says "run the remap before syncing it" — stale code text, since the remap was the one-time migration tool (see Scripts above) — and [`CRM_INTEGRATION.md`](../CRM_INTEGRATION.md) §9 lists the known unbound rows but has no procedure for binding one. `crmIsConfigured()` / `activeCrmName()` serve the sync services. Teardown enumerates the ledger, removes only notes held by the active provider (HubSpot-era notes are left alone) and attempts each note independently.
- **crm-notes.repository.ts** — the `crm_notes` ledger: one row per note with its `provider`, target and owner (document or calculator config); idempotent on `(provider, note_id)`.
- Callers: `server/modules/documents/sync.service.ts` and `server/modules/calculator-configs/sync.service.ts` (auto-sync on create is gated by `AUTO_SYNC_TO_HUBSPOT`, a legacy name — it posts to the active CRM).

### HubSpot (`server/modules/hubspot/`) — DORMANT LEGACY
> Retired 2026-08-31; the account no longer exists, so there is no rollback. The code is kept (renames are deferred) but unused: the webhook processor and startup backfill start only when `CRM_PROVIDER=hubspot`, and the `/api/v1/hubspot/*` routes are still mounted but unused. The description below is the HubSpot-era design, kept for reference — do not build on it.

- **Client (hubspot.client.ts):**  
  Wraps `@hubspot/api-client`, caches auth token, handles rate limiting.
- **Mapper (hubspot.mapper.ts):**  
  Transforms HubSpot property enums → internal `companyType`, `segmentType`, `lifecycleStage` fields.
- **Routes (hubspot.routes.ts):**  
  Mounts read-only `/pipelines` (Bearer-auth) PLUS the Sprint 5 webhooks subrouter.
- **Backfill Script (scripts/hubspot-backfill.ts):**  
  On startup, if `HUBSPOT_AUTO_BACKFILL=true` and companies table is empty, the backfill runs in the background while `/health` responds normally — only when `CRM_PROVIDER=hubspot`, so never in production today (`server/index.ts` gates it, and the function itself skips with a WARN otherwise).

#### Sprint 5: Webhooks (`server/modules/hubspot/webhooks/`)
- **webhooks.routes.ts** — two endpoints:
  - `POST /api/v1/hubspot/webhooks` (public, HMAC v3 verified).
  - `POST /api/v1/hubspot/refresh` (Bearer-auth, max 100 ids).
- **webhooks.controller.ts** — receiver inserts events into
  `hubspot_webhook_events` and returns 200 in <10ms; refresh
  refetches by `companies.id` UUID and upserts.
- **webhooks.processor.ts** — Self-rescheduling `setTimeout(5000)` worker
  started by `server/index.ts` (Sprint 5.F.1 — replaced `setInterval`
  to eliminate re-entrancy). Picks up `status='pending'` rows ordered
  by `(occurred_at, id)`, fan-outs to per-event upsert / filter / delete
  logic via repository helpers (`deleteDealsByCompanyId`,
  `deleteCompanyByHubspotId`, `findCompanyByHubspotId`).
  `MAX_ATTEMPTS=5` retry budget with exponential backoff
  (`attempts × 30s` since `received_at`) — full budget spans
  ~7.5 minutes; previously exhausted in ~25 seconds because the
  backoff column was never wired (Sprint 5.F.1 fix). Company-
  deletion path is wrapped in `db.transaction()` so the
  `DELETE deals` + `DELETE companies` pair is atomic.
- **webhooks.schemas.ts** — Zod enum (`SUPPORTED_SUBSCRIPTION_TYPES`)
  + `webhookBodySchema` (array; min 1). Unknown subscription types
  are logged and dropped (200 with `malformed:true`) — never 4xx,
  to avoid HubSpot retry storms.
- **webhooks.repository.ts** — `insertEventIfNew` (idempotent via
  `ON CONFLICT DO NOTHING` on `hubspot_event_id`), `listPendingEvents`,
  `markProcessed` / `recordFailure` / `markFailed`.
- **verify-hubspot-signature middleware** — HMAC SHA-256 v3 source
  string = `${method}${uri}${rawBody}${ts}`, 5-min timestamp window,
  constant-time `crypto.timingSafeEqual`. The URI is built from
  `env.APP_PUBLIC_URL` (Sprint 5.F.1 — was previously
  `${req.protocol}://${req.get("host")}` which was proxy-header
  derived and could in theory be flipped by `X-Forwarded-Proto`
  injection). The raw body parser (`express.raw`) is mounted
  path-scoped at the webhook URL in `app.ts` BEFORE `express.json()`
  — otherwise the global JSON parser would consume the body and
  break HMAC verification.

## Sprint 2.7 Shared Helpers (Reuse in Future Sprints)

**These three helpers are critical for Phase 3+ modules (calculator-configs, documents, listings, webhooks):**

### 1. `shared/ttl-refresh.ts` — Background Sync Scheduling
**Why:** Deduplicates the "serve stale, refresh async" pattern across companies, deals, and (future) listings.  
**Key Entry Point:** `scheduleTtlRefresh(config: TtlRefreshConfig)`

- Guard: checks if `enabled && ttlMs > 0 && ageMs >= ttlMs`.
- Queues work via `setImmediate()` (non-blocking return to caller).
- Wraps refresh callback with try/catch + structured logging.
- **Contract:** Pass `lastSyncedAt`, `ttlMs`, `enabled`, `refresh` callback, log label, and structured context.

**Use in future modules:** Any listing that syncs from an external source (the active CRM, an external calculator engine, etc.) can reuse this instead of duplicating `companies.service` logic. Companies and deals already call it provider-aware (monday.com in production).

### 2. `shared/dto-parse.ts` — Response DTO Validation
**Why:** Separates output validation (→ 500 InternalError) from input validation (→ 400 ValidationError).  
**Key Entry Point:** `parseDtoOrInternalError<Schema>(schema, data, context)`

- Parses data against Zod schema.
- On failure: logs entire projection object + detailed error paths (operator debugging).
- Throws `InternalError` (not `ValidationError`), so error-handler returns 500 (not 4xx).
- **Contract:** Always pass a freshly-constructed DTO object (not raw DB rows), so logs don't flood with sensitive blobs.

**Use in future modules:** Wrap every `toPublic()` or similar projection with this. Protects against typos in SELECT statements or Drizzle query changes that accidentally drop fields.

### 3. `shared/build-page.ts` — Cursor Pagination
**Why:** Unifies the "fetch limit+1, determine hasMore, encode nextCursor" logic.  
**Key Entry Point:** `buildPage<TRow, TPublic>(rows, limit, toPublic, toCursor) → PageResult<TPublic>`

- Fetches `limit + 1` rows to detect if more exist.
- Projects rows → DTO inside the helper (avoids mapping twice).
- Returns `{ items, nextCursor, limit }`.
- **Contract:** Pass row type, limit, projection function, and cursor extractor.

**Use in future modules:** Any listing endpoint (calculator configs, documents, saved listings) calls repository with `limit + 1`, then passes result to `buildPage()`. Cursor encoding is in `shared/pagination.ts`.

## Error Handling Envelope

All errors are caught by `middleware/error-handler.ts` and serialized as:
```json
{
  "error": {
    "code": "VALIDATION_FAILED",
    "message": "...",
    "details": { /* optional */ }
  }
}
```

**Error Codes (shared/errors.ts):**
- `400 VALIDATION_FAILED` — ZodError on request input.
- `400 REQUEST_PARAM_INVALID` — UUID or other param parse failure.
- `401 AUTH_INVALID_CREDENTIALS` — Wrong email or password.
- `401 AUTH_TOKEN_EXPIRED` — JWT expired or malformed.
- `401 AUTH_REQUIRED` — Missing Bearer token.
- `403 AUTH_FORBIDDEN` — Insufficient role (admin gate).
- `404 NOT_FOUND` — Resource doesn't exist.
- `409 ALREADY_EXISTS` — Unique constraint violation.
- `409 HUBSPOT_SYNC_IN_PROGRESS` — a CRM sync for the same document / calc-config is already running (legacy code name).
- `429 RATE_LIMITED` — Too many requests.
- `502 HUBSPOT_UNREACHABLE` — the active CRM (monday.com in production) is unreachable, or the row is not bound to a CRM item. Legacy code name, kept deliberately: the frontend matches it literally.
- `500 INTERNAL_ERROR` — Server projection mismatch or unhandled throw.

## Deployment & Startup Sequence

1. **Build:** `npm run build:server` (tsc → `dist/server/`)
2. **Entrypoint:** `node --loader tsx server/index.ts` (or `tsx server/index.ts` in dev)
3. **Startup:**
   - Load env from `.env` or Docker runtime.
   - Validate schema (crash if missing/invalid).
   - Initialize DB pool.
   - Create Express app.
   - Bind to `PORT`.
   - If `CRM_PROVIDER=monday`: assert the pinned monday API version, then start the monday webhook processor (5s poll) and `startMondayMaintenance()` (scheduled backfill + hourly health log). If the assertion fails, neither starts and an error is logged.
   - The HubSpot startup backfill (`HUBSPOT_AUTO_BACKFILL`) and the HubSpot webhook processor start only when `CRM_PROVIDER=hubspot` (dormant).
4. **Shutdown:** SIGTERM/SIGINT → drain in-flight requests (10s timeout) → close HTTP server → stop the webhook processors → close the Puppeteer browser → drain DB pool → exit.

## Key Entry Points for New Developers

1. **Understand request flow:** `app.ts` → middleware stack → `modules/*/routes.ts` → controllers → services.
2. **Add a new route:** Copy `modules/companies/` structure, mount in `app.ts`.
3. **Read from the CRM:** go through `monday.backfill.ts` (`upsertOneCompany` / `upsertOneDeal`, as `monday.refresh.ts` and the webhook processor do) and call `scheduleTtlRefresh()` in the service with a provider-aware `enabled` / `refresh`. Do not add new code on `hubspot.*` (dormant legacy).
4. **List pagination:** Use `buildPage()` + cursor helpers in `shared/pagination.ts`.
5. **Output validation:** Wrap projections with `parseDtoOrInternalError()`.
6. **Errors:** Throw `AppError` subclasses; `error-handler` catches + serializes.
